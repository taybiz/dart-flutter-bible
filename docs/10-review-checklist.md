# 10. Review Checklist

- [ ] **10.1** Dependencies point inward? (No domain → application/UI imports.) Enforced by the `dart_arch_test` boundary test over the resolved import graph in CI — not by melos?
- [ ] **10.2** Any `throw`/`try`/`catch`/`on Exception` inside domain, use cases, or datasource *business* code? (Allowed: the single `TaskEither.tryCatch`/`Either.tryCatch` wrapping the third-party call in adapter methods, and the UI ring — hand-rolled `try/catch` inside adapters is *not* allowed.)
- [ ] **10.3** Entities immutable + equatable? Operations return new instances?
- [ ] **10.4** Every repository contract has **≥2 repository adapters** and runs the contract suite against all of them? (A package that publishes no adapter is out of scope — §3.6 — but its contract suite, and the suite's shape, still stand.)
- [ ] **10.5** Failures typed, layer-mapped (datasource failure ≠ domain failure leaked)?
- [ ] **10.6** sqlite3 done with drift? Any other ORM/raw sqlite3 in the tree?
- [ ] **10.7** Any unapproved builder/codegen (freezed, json_serializable, `riverpod_generator`, `injectable`)? If yes — why?
- [ ] **10.8** Tests: shouldly only (no `expect()` mixing), Given/When/Then names, both Either sides covered, mocks only at the use-case seam with mocktail?
- [ ] **10.9** Every declaration and public member carries a terse `///` doc comment (1–2 lines, what+why)? **No `///` file headers** (that forces a `library;` — barrel files only)? Use cases documented?
- [ ] **10.10** Use-case `call()` takes discrete business params (`id`, `userName`, …), never cargo/container objects?
- [ ] **10.11** Dart named parameters everywhere (sole exceptions: single positional `ref`/`message`/`value`)? Flutter widgets follow Flutter conventions?
- [ ] **10.12** One hand-written barrel per package (`lib/<package>.dart` re-exports `lib/src/`), no `src/` imports across packages?
- [ ] **10.13** Every operation that steps more than once (or decides a rule by reading and then writes) takes a **required** `UnitOfWork` — and the repository contracts stay transaction-free: no `uow` parameter, no `clearAll`? A store that cannot roll back is wired with `noOpUnitOfWork` at the composition root, stated rather than defaulted? The adapter keeps the seam — publishes the open unit, routes every read through it, joins on re-entrance, retries a busy store?
- [ ] **10.14** Example code in tests first? `example/` (singular — the pub.dev convention) only for packages or a genuine need (e.g., core facade for GUI)? No code in READMEs/prose? Doctrine snippets small and tight?
- [ ] **10.15** D.R.Y.: no rule or decision restated in a README, AGENTS.md, or comment when the bible already has it? Project docs link to doctrine — they don't copy it. Does `BACKLOG.md` stay a terse queue (one unique actionable item each, pick-up-able by automation) rather than a diary or a running commentary — with keen decisions in `CHANGELOG.md` and keep-your-footing knowledge in `AGENTS.md`?
- [ ] **10.15a** Deviation triage consistent: every divergence from the bible that the repo **must live with** (bible vague/wrong) is named in `AGENTS.md` under "Deviations"; every **fixable defect** (code clearly in the wrong) is a `BACKLOG.md` item to fix — never recorded as an accepted divergence (bible §1.3)?
- [ ] **10.16** `melos.yaml` anywhere? (A leftover from melos 6.x — migrate.) Melos scripts declared in the root `melos:` block and wired — `melos run analyze`/`test` are what CI and agents call, never raw per-package commands? Melos kept out of boundary enforcement (that is `dart_arch_test`'s job)?
- [ ] **10.17** `dart analyze --fatal-infos --fatal-warnings` reports **zero diagnostics** (no errors, no warnings, no infos) and `dart test` green across the workspace?
- [ ] **10.18** No `TODO`/`FIXME` comments anywhere? Deferred work lives in the roadmap doc, not code.
- [ ] **10.19** Any `// ignore:` is per-line with a reason — no `ignore_for_file` or blanket suppressions?
- [ ] **10.20** Error style **declared** — the barrel doc comment, the README, and (on any deviation from the `Future<Either<...>>` default) `AGENTS.md` all state whether consumers get FP-style tuples or plain exceptions?
- [ ] **10.21** GUI-changing work ships with interaction coverage that runs in CI — widget and/or `integration_test` (`flutter test integration_test/…`)? Marionette, if used, has `MarionetteBinding` initialized **only** under `kDebugMode` (no release surface), and `marionette_mcp` stays a dev tool, never an app dependency?
- [ ] **10.22** State management structured and singular (§8.2): one approach per app; app state in an explicit state layer (provider/cubit/notifier), not widget-local `setState`; no business logic in the state holder; zero state-package imports (`flutter_riverpod`, `flutter_bloc`, …) in the domain ring (domain/usecases/datasources); dependencies resolved at the composition root only?
- [ ] **10.23** A package that publishes **no adapter** says so in its `AGENTS.md`, still ships a contract suite that takes *any* implementation, and keeps any reference implementation out of the published archive (§3.6)?
